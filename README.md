# 农村集市摊位抽签收费食品留样与投诉平台

面向乡镇集市的一体化管理平台，覆盖 **报名 → 审核 → 抽签 → 缴费 → 入场核验 → 巡查 → 食品留样 → 投诉处理 → 信用与调整追溯 → 复盘看板** 全链路。

- 后端：Spring Boot 3 + Spring Security(JWT) + Spring Data JPA
- 前端：Vue 3 + Vite + Element Plus + ECharts
- 数据库：PostgreSQL

## 角色与功能

| 角色 | 功能 |
| --- | --- |
| 摊主 VENDOR | 赶集日前报名（品类/车辆尺寸/用电/是否熟食活禽/证照照片/历史经营记录）、查看抽签结果与入场码、缴费、上传食品留样（照片/批次/保存位置）、查看信用与调整记录、提交申诉（费用/扣罚/边界争议）、查看**摊位图公示与边界争议/整改结论** |
| 市场工作人员 STAFF | 扫码入场核验并拍摄摊位布置、登记实际品类与是否按位摆摊、巡查登记（卫生/明码标价/缺斤少两/占道/用电安全）、**摊位边界争议现场拍照并在图上标注实际边界** |
| 乡镇管理员 ADMIN | 集市与摊位区域管理、报名审核、组织抽签（种子+规则快照留档、一键复核）、投诉处理（可联动信用扣分）、**边界争议认定（超抽签面积→整改+扣分；抽签图不清晰→更新摊位图并免除本次扣罚）**、**摊位图风险点与重新测量后发布更新图**、调整（临时调位/雨天调位/费用减免/保证金扣罚/信用调整/品类变更，原因与来源必填）、复盘看板（高投诉品类/拥堵区域/收费到账/食品安全风险）、审计日志 |
| 消费者（免登录） | 凭摊位号提交投诉（腹泻/价格/缺斤少两等） |

## 公平与可追溯设计

1. **抽签可复核**：抽签算法为确定性算法——同一「输入快照 + 随机种子」重放结果必然一致。每次抽签固化规则快照与输入快照，管理端提供「复核」按钮重新演算比对，防止结果被篡改。
2. **规则内置**：老摊主（历史经营≥3次且信用≥60）优先；熟食仅入冷链区（有电源）；活禽仅入隔离区；用电需求仅配有电源摊位；车辆超限排除；消防通道等停用摊位不参与分配。
3. **调整必留痕**：临时调位、费用减免、保证金扣罚、信用调整、品类变更均必须填写**原因**与**来源**（雨天/投诉/巡查/争议/摊主申请/政策），生成 Adjustment 记录并写审计日志，摊主端可见，避免"规则被人为改变"的质疑。
4. **边界争议可追溯、图调整有依据**：工作人员现场拍照并在图上**标注实际边界**；管理员三选一认定——①一方超抽签面积→生成整改通知并扣信用（同样走 Adjustment 留痕，摊主可见）；②抽签图本身不清晰→**免除本次扣罚**并对该区域建立"重新测量"任务；③双方均未违规→仅办结。同一区域边界争议累计达阈值（2 起）自动标记为**摊位图风险点**；管理员在下次集市前重新测量并发布更新版摊位图（版本号递增、更新原因与测量依据必填），通过公开的摊位图版本向**新老摊主**公示调整依据。
5. **全链路审计**：抽签、审核、核验、巡查、边界争议登记/认定/免罚/整改复查/摊位图发布、投诉处理、调整等敏感操作全部写入审计日志。

## 一键启动（Docker Compose）

```bash
docker compose up -d --build
```

- 前端：http://localhost （80 端口）
- 后端：http://localhost:8080
- 数据库：PostgreSQL localhost:5432（market / market123）

首次启动自动建表并初始化演示数据（账号、区域摊位、一个报名中的集市）。

## 本地开发

```bash
# 1. 准备 PostgreSQL（建库 market，用户 market/market123），或用 docker 单起数据库：
docker run -d --name market-db -p 5432:5432 \
  -e POSTGRES_DB=market -e POSTGRES_USER=market -e POSTGRES_PASSWORD=market123 postgres:16-alpine

# 2. 后端（默认连 localhost:5432/market，可用 DB_URL/DB_USER/DB_PASSWORD 覆盖）
cd backend && mvn spring-boot:run

# 3. 前端（Vite 代理 /api 与 /files 到 8080）
cd frontend && npm install && npm run dev   # http://localhost:5173
```

## 本题验证方式（完整业务闭环）

1. **报名**：用 vendor1~vendor6 登录 →「摊位报名」选择"十月十五大集"提交（品类/车辆/用电/熟食活禽/证照照片/历史记录）。
2. **审核**：admin 登录 →「集市与报名审核」→ 报名审核 → 全部通过。
3. **抽签**：admin → 集市列表"截止报名"→"组织抽签"输入种子执行；「抽签管理」查看结果明细与规则/输入快照，点"复核"应显示**复核通过**。
4. **缴费**：vendor1 →「抽签结果与缴费」查看摊位号/入场时间/收费项目/保证金/禁止事项/入场码，缴纳费用。
5. **入场核验**：staff1 →「入场核验」输入摊主入场码 → 确认实际品类、按位摆摊、上传布置照片。
6. **巡查**：staff1 →「巡查登记」对摊位登记卫生评分、明码标价、缺斤少两、占道、用电安全。
7. **留样**：vendor1（熟食）→「食品留样」上传留样照片、批次、保存位置。
8. **投诉**：访问 /complaint（免登录）凭摊位号提交"腹泻"投诉；admin →「投诉处理」办结并联动扣信用。
9. **调整追溯**：admin →「调整与追溯」发起雨天调位/费用减免/保证金扣罚/信用调整（原因+来源必填）；vendor1 →「信用与追溯」可见全部调整的原因与来源。
10. **复盘**：admin →「复盘看板」查看高投诉品类、拥堵/占道区域、收费到账、食品安全风险；「审计日志」查看全部敏感操作留痕。
11. **摊位边界争议调解（本功能）**（需先完成报名→审核→抽签，使相邻摊主拿到摊位）：
    - staff1 →「边界争议调解」：选择集市与相邻两摊（如 B-05 王老二 / B-02 李大嫂），填写双方主张、**上传现场照片并在照片上点击标注实际边界线**、填写实测说明（如通道 2.1m）后提交。
    - admin →「边界争议与摊位图」：对争议点"认定处理"。
      - 选 **一方超抽签面积**：指定超面积方（如 B-02）、扣分（默认 5）→ 自动生成整改通知 + 信用扣分；vendor2 →「摊位图公示」可见涉及自己的争议结论、整改要求与信用变动，「信用与追溯」可见来源为"争议处理"的调整记录。
      - 再登记一起同区域争议并选 **抽签图不清晰** → **免除本次扣罚**（信用不再下降），该区域进入风险点"测量中"。
      - 同一区域累计 2 起争议 → 自动进入「摊位图风险点」；admin 点"发布更新图"，上传重新测量后的摊位图、填写更新原因与测量依据后发布，风险点转为"已发布更新图"。
      - 老摊主（vendor1）与新摊主登录后在「摊位图公示」均能看到更新图版本、更新原因与调整依据；该接口免登录也可访问（`GET /api/meta/stall-map-versions`，仅返回已发布版本）。
    - admin →「审计日志」可见 BOUNDARY_REGISTER / BOUNDARY_PENALIZE / BOUNDARY_WAIVE / BOUNDARY_RECTIFY_VERIFY / STALL_MAP_PUBLISH 留痕。

- `mvn package` 后端构建通过，含 6 个抽签算法单元测试（确定性重放、熟食→冷链区、活禽→隔离区、用电/车长约束、无兼容摊位落选、品类区域匹配），全部通过。
- `npm run build` 前端构建通过，构建产物经 `vite preview` 代理实际访问验证（SPA 路由回退、/api 代理均正常）。
- 后端连本地 PostgreSQL 15 实启动成功，种子数据自动初始化。
- 通过 curl 完成两轮完整业务闭环接口级冒烟：
  - 第一轮：6 家报名→审核→抽签（种子 20261015）→**复核一致(match=true)**→缴费→扫码→入场核验→巡查→留样→公开投诉→投诉处理联动扣信用→雨天调位（目标摊位占用校验生效）→费用减免→保证金扣罚→看板统计与审计日志均返回正确数据。
  - 第二轮（经前端代理端口）：新集市开放报名→2 家报名→审核→截止→抽签→复核通过；果蔬摊主分入 D 区、用电百货摊主分入 A 区带电摊位，区域/用电约束生效。
- 安全校验：未登录访问管理接口返回 403、摊主访问管理接口返回 403、响应不返回密码字段（@JsonIgnore）。
- 文件上传（证照/留样照片）与 /files 静态访问验证通过。
- **摊位边界争议调解（本功能）在本地 PostgreSQL 15 实启动后端，curl 接口级冒烟通过**：
  - 工作人员登记争议：上传现场照片 + 图上标注实际边界（坐标 JSON）+ 实测说明，生成状态为"待认定"的争议单，写 BOUNDARY_REGISTER 审计。
  - 认定"一方超抽签面积"：指定 B-02 李大嫂为超面积方 → 自动生成整改通知（限期 24h、附现场照片与实测边界）、信用 100→95、生成来源为 DISPUTE 的 CREDIT_ADJUST 调整记录；双方摊主各自接口均能看到该争议；整改复查通过后状态转"已整改"。
  - 认定"抽签图不清晰"：第二起同区域争议 → `waived=true` 免除本次扣罚（信用仍为 95 未再扣），B 区自动进入"待重新测量"。
  - 风险点：同区域累计 2 起争议 → `/api/admin/boundary-risk-points` 标记 B 区风险点（MEASURING）；发布 v1 更新图后自动转 RESOLVED，待测量任务关闭；再次发布版本号正确递增为 v2。
  - 公示：已发布摊位图经公开接口 `GET /api/meta/stall-map-versions` 免登录可查（新摊主可见），仅返回 PUBLISHED 版本、不泄露 MEASURING；摊主端「摊位图公示」展示版本/更新原因/测量依据。
  - "双方均未违规"分支不扣分、不生成整改，仅办结。
  - 安全：摊主访问 `/api/admin/boundary-risk-points` 返回 403、未登录访问工作人员争议接口返回 403。
  - `mvn test` 原有 6 个抽签单元测试在新增实体/服务后仍全部通过；`npm run build` 前端构建通过（新增 staff/admin/vendor 三个边界页面与 BoundaryMarker 组件均成功打包）。
